预测式专家复制

稀疏 MoE 的每一层只把 token 路由到当下最热的专家上，于是热点专家所在的 rank 成为整层的关键路径。而下一层的热点专家，在当前层就能提前知道：把目标层的路由 gate 作用到当前层的隐状态上，即可得到那个层自己的专家选择。本方案据此提前把专家权重复制到即将需要它的 rank，并把这次权重搬运完全藏在两层之间本来就要执行的一段 Attention 之后。

模型 Qwen3-30B-A3B 层数 48（可达源层 44） 拓扑 DP = EP = 8 硬件 8 × H100 SXM 放置开销 0 次 host 读取
摘要

本文描述一种在 MoE 推理中动态复制专家权重的机制。它在第 L 层的 MoE 尾部读取该层隐状态，用第 L+1 层自己的 gate 求出一份专家负载预测；据此在设备端选出一个目标 rank，用单边 put 把该专家的权重写入其副本槽；写入在 L+1 层的 Attention 期间完成，并在该层路由之前发布为新的路由表。整条路径上，放置计划从不到达主机。

测量结论是分裂的：放置本身是负成本，它卸掉关键路径上 26–36% 的失衡而几乎不增加开销；预测则是全部开销所在，也是该方案在短 prompt 上净为负的原因。在长 prompt、低并发区间，端到端 prefill TTFT 取得 2–5% 的可复现收益。

方案总览

整个方案可以拆成四个动作，图 1 按顺序给出。判断依据是这样一个事实：某一层的路由结果由 logits = hidden_states @ gateᵀ 决定，而 gate 的权重本来就在手里。因此用目标层的 gate 去作用于当前层的隐状态，得到的就是目标层自己的专家选择——这不是启发式猜测，而是一次真实的 gate 求值，唯一的误差来源是隐状态旧了一层。

贯穿全篇的约定

源 rank 路由

路由表以 (源 rank, 逻辑专家) 为键。因此同一源 rank 上选择同一逻辑专家的 token，必然解析到同一个物理副本——逐 token 的选择退化为一次查表，而一个副本恰好卸掉半个专家，卸载量永远是整数。

预测的量

峰值 rank 自己的分布

放置只能把负载从最热的那个 rank 上搬走，且只能在该 rank 持有的专家中选择。因此真正重要的量是峰值 rank 自身的分布，而非全局专家负载。

距离的由来

lookahead 是结果，不是旋钮

预测精度随距离增大而下降（34.9 / 34.4 / 33.5 / 32.1% 对应 lookahead 1 / 2 / 3 / 4），但重叠窗口决定了距离的下界。该下界由传输方式给出，故距离取 1。

2

两条 stream 与三个同步点

图 1(c) 说明窗口是什么，图 2 说明这个窗口靠什么撑开。关键在于本方案使用了两条 CUDA stream：计算流按层顺序执行，另有一条专用的预测流承载权重搬运。三条搬运步骤——写入、建立可见性、落到副本槽——全部排在预测流上，因此它们与计算流上的后续层真正并行，而不是被塞进时间轴上的某段空隙。两条流只在两个事件处相交：计划写好后记录一个事件，目标层取用前等待那个事件。

实现组成

表 1 列出构成该方案的六个计算单元。前三个用 Triton 编写、处理专家负载与放置决策；后三个用 CUDA C++ 调用 NVSHMEM，处理权重搬运及其可见性。所有 Triton 内核都与一份张量实现互为断言：融合版本必须与其逐位一致，后者作为参照实现保留。

单元类型频次职责
_fused_predict_kernel Triton1 / 源层 gate 矩阵乘、top-8 选择与逐专家计数合并于一个 program。128 个专家补齐到 2 的幂，使整行 logits 常驻寄存器——此前需要落地的五份 [tokens, top_k] 中间量至此全部消失。选择结果与参照实现逐位一致：fp32 强制 IEEE 而非 TF32，bf16 在选前把累加器舍回 bf16，并列时取小。
plan_replicas_fused Triton1 / 层 一层的全部放置决策、预算记账与两张计划表，由单个 program 完成。所有归约的规模不超过 ep_size × per_rank 个整数，因而无需跨 block 协商——这也移除了最后两处两个 rank 可能以不同次序归约、进而得出不同计划的位置。全部算术以加倍单位进行，使"卸掉半个专家"始终是整数。
publish_plan_fused Triton1 / 层 把路由表改成计划要求的样子。先回退，再放置：一个槽从专家 a 改给专家 b 时同时属于两者，若在放置之后回退，会清掉刚刚认领的那一行。副本行可能落在其规范行的下方，故按物理行升序书写——假定顺序为 [规范行, 副本行] 会在这些情形下写入错误的行。
put_expert CUDA C++
NVSHMEM		1 / 层 所有 rank 都执行；持有该专家的 rank 把其权重行写入目标 rank 的暂存区。由本 rank 是否持有该专家，是在设备上依据计划判定的——这是该设计的核心，它使计划无需回到主机。实测 9.00 MiB 单边写入为 47.6 µs（设备发起）对 53.7 µs（主机发起）：耗时相同，主机被移除。
nvshmemx_barrier_all CUDA C++1 / 层 由主机下发，且不依赖任何计划取值，因而不会把计划拉回主机。其作用是建立可见性。CUDA event 无法替代：一个曾得出相反结论的探针，其检查区间内混入了一次 dist.barrier()；去掉它之后 112 个权重张量中有 51 个是错的。
drain_expert CUDA C++1 / 层 所有 rank 都执行；目标 rank 把暂存区数据拷入副本槽。用整个 block 搬运 9 MiB 实测 206 µs，而用 32 个 block 为 47.6 µs——单个 block 只能用自己的 load/store 单元，无法借用拷贝引擎。

5

讨论：方案的边界

已经确定

两半的符号相反

放置是负成本：它卸掉失衡，本身几乎不增加开销，捕获了上限 5.26% 中的约 70–80%。预测是全部开销所在——每层 44 次 gate 矩阵乘与 44 次集合通信，也正是短 prompt 上净为负的原因。因此该方案的成本在"使能"的一半，而非"动作"的一半。

尚未解决

全部正收益都是 prefill

输出长度为 1 token 意味着收益不会被摊薄到整个请求上。真实负载的输出是数百至数千 token，而副本是跨前向常驻的——解码阶段是否要为此付出代价，仍无定论。这是唯一能否定上述全部结论的变量。

已被证伪

两个被实测否决的设计

其一，让一个源层跨多个目标层做预测：四层的 gate 作用于同一份隐状态会选出几乎相同的专家，四分之三的目标实际使用了并非自己的分布，收益自 26.9% 跌至 3.7%。其二，把快照规约改为设备端实现：其天花板为 8.78 ms，而缺口为 17.09 ms——即使实现为完全免费，方案仍落在 +4.8%。
