# Predictive expert replication for MoE inference

Status: ready-for-agent  
Labels: ready-for-agent  
Scope: CUDA implementation in the separately pinned vLLM fork, targeting Qwen3-30B-A3B on 8x H100 SXM first and DeepSeek-V4-Flash second. This document also fixes the contract for the later MindSpeed-RL Ascend port.  
Revision: **rewritten 2026-08-29** after a working host-planned implementation was measured end to end and found net negative. Every quantity below is measured on this node unless marked as derived or as an extrapolation; `bench/RESULTS.md` carries the evidence and `CURRENT-STATUS.md` the state.

## Problem Statement

A hot logical expert makes its canonical owner the slowest EP rank. Token dispatch and combine are collectives, so every rank waits for that one rank, and a single hot expert bounds the whole forward. Measured on this node with real Korean prompts, the per-layer **critical-path imbalance** is 1.8852 on Qwen3-30B-A3B and 1.9622 on DeepSeek-V4-Flash, against multinomial noise floors of 1.15 and 1.15 — so the skew is real and far above sampling noise. On DSV4 one rank holds 38.46% of a layer's tokens where an even split is 12.50%, and a layer's peak reaches 3.077 times its own mean.

Native EPLB can create redundant physical experts, but it decides placement from a historical actual-load window and changes placement every `step_interval` steps, thousands of forwards apart. That cannot follow bursty or phase-changing traffic.

The operator-facing goal is **lower TTFT** — mean and p99 — at equal request load. The earlier TPOT goal is retired: decode is settled negative because below one block per expert the MoE kernel pads every touched expert to the same block count, so the imbalance costs nothing to begin with.

**A working implementation of this feature already exists in the tree and is net negative.** It plans on the host, and measured against a stock server on 400 requests it costs **+31.5% mean TTFT** while a perfect placement could return at most **5.05% of a prefill step**. This spec exists because the reason is now understood precisely enough to be designed against, not because the idea failed.

## Solution

Add **Device-planned placement**: the same predictive controller, with the host removed from the per-forward path entirely.

The current layer's **cross-layer gate** estimates the next layer's logical-expert loads for every valid routed token. A deterministic **argmax on the device** turns the **global predicted-load snapshot** into one **replica placement plan** per layer. The canonical owner writes the expert into a symmetric **staging workspace** on the target rank with a one-sided put, the target copies it into its **replica slot**, a device scatter publishes the **source-local physical map**, and the target layer's MoE reads the replica. No step of that requires the host to know the plan.

Why the host must go, quantitatively. Three measurements, all on this node:

- **The transfers are not the problem.** They are 0.32% of GPU time and genuinely overlapped. Four earlier rounds of design chased them.
- **The cost is prediction's per-layer footprint, amplified by desynchronisation.** Prediction adds ~2.2 ms of GPU work per prefill window but the token collectives grow **+39.9 ms** with the same kernel count and the same byte volume — pure waiting, because ~700 extra launches and 43 host synchronisations push each rank's arrival at the next collective apart. The amplification is about 18x.
- **That cost is linear in the number of predicting layers**: 7.00 ms of extra collective waiting per source layer at 11 layers, 7.50 ms at 43 — within 7%. So reducing per-layer work reduces cost proportionally, and this is what makes the design tractable rather than a hope.

The host appears in three places today, and each has a device replacement that has been verified rather than assumed:

| host involvement today | why it exists | device replacement |
| --- | --- | --- |
| a D2H synchronisation per predicted layer | the planner is host Python | deterministic argmax over 128 integers on the device |
| `ncclSend`'s peer is a host `c_int` consumed at enqueue | the transport channel is chosen then | one-sided put; the address is computed on the device |
| the routing maps are written with host scalars | the plan lives on the host | a device scatter — **and routing already consumes those maps as device tensors** |

With the plan never leaving the device, the **prediction lookahead** can drop to 1 and the **overlap window** becomes the target layer's Attention, which is the shape the operator asked for and which the current hook positions cannot express.

## User Stories

1. As a serving operator, I want predictive expert replication disabled by default, so that existing deployments retain their current behaviour.
2. As a serving operator, I want every TTFT claim about this feature to come from three arms — feature disabled, prediction only, and placing — so that I am never shown the cost of placement mistaken for the cost of the feature.
3. As a serving operator, I want the feature to reduce mean and p99 TTFT against a **stock** server, so that the comparison matches what I would actually deploy.
4. As a serving operator, I want the achievable ceiling stated and re-measured on my hardware before any optimisation work, so that effort is never spent chasing a gain smaller than its own overhead.
5. As a serving operator, I want an explicit stop condition in the spec, so that a negative result ends the project instead of being absorbed into further tuning.
6. As a serving operator, I want no host synchronisation anywhere on the per-forward path, so that the CPU keeps its run-ahead and the engine does not become launch-bound.
7. As a serving operator, I want prediction's per-layer work minimised rather than its transfers, so that the optimisation targets the cost that was measured rather than the one that was assumed.
8. As a serving operator, I want the number of predicting layers to be a knob, so that prediction's cost can be traded against coverage on hardware where the ratio differs.
9. As a model operator, I want each logical expert's canonical owner to remain fixed, so that replicas improve execution placement without changing model ownership.
10. As a model operator, I want the initial physical layout to be the rank's canonical experts plus one inactive replica slot, so that memory cost and the comparison with Native EPLB are controlled.
11. As a model operator, I want model initialisation to finish layout normalisation before readiness, so that TTFT excludes startup rearrangement.
12. As an inference request, I want routing to preserve logical expert semantics whether a replica exists or not, so that placement never changes generated output beyond floating-point tolerance.
13. As a source rank, I want all my tokens for a given logical expert to use one physical copy, so that routing is deterministic source-rank routing rather than token-level.
14. As a distributed worker, I want every rank to derive a bit-identical plan from the same snapshot, so that no plan broadcast or leader is needed and a send never pairs with a missing receive.
15. As a distributed worker, I want the device argmax asserted bit-identical to the retained host planner, so that moving the decision to the device cannot silently change it.
16. As a distributed worker, I want no per-forward collective to branch on per-rank state, so that ranks cannot diverge and deadlock.
17. As a distributed worker, I want every event either waited on a stream or synchronised unconditionally and never polled, so that timing differences between ranks cannot become control flow.
18. As a serving operator, I want the transfer to land through a symmetric staging workspace and a local copy, so that the model's own weight allocation is untouched by the interconnect layer.
19. As a serving operator, I want the target rank to wait for the weights on its own stream before using a replica, so that a forward cannot execute against partially copied weights and the host is not blocked to guarantee it.
20. As a serving operator, I want non-participating ranks to proceed to the next EP collective, so that activation adds no global barrier.
21. As a model operator, I want the routing maps published by a device scatter, so that publishing a placement costs no host round trip and no map inversion.
22. As a model operator, I want a replica reverted when the current plan no longer wants it, so that a placement does not go on shedding load from an expert that is no longer hot onto a rank that may now be the peak.
23. As a model operator, I want a forward below the block-quantization bar to change nothing, so that decode and dummy forwards neither place nor revert.
24. As a developer, I want placement suppression decided from a value every rank agrees on before anything is recorded, so that a forward which predicts nothing cannot silently revert every layer.
25. As a developer, I want the transfer budget to bound what it claims to bound, so that a knob named for transfers is not in fact a coverage cap.
26. As a developer, I want expert-weight bytes in flight bounded, so that replica transfer cannot saturate the interconnect that dispatch and combine already share.
27. As a developer, I want the per-layer replica cap defaulted from measurement, so that a budget buys coverage across the model rather than depth on its earliest layers.
28. As a developer, I want the counting kernel tested against the existing implementation as a reference, so that a fused rewrite whose failure mode is a wrong count is caught by construction.
29. As a developer, I want `prediction_lookahead_layers = 1` rejected until the launch point moves, so that the value that looks most attractive cannot silently produce a zero-length overlap window.
30. As a benchmark owner, I want imbalance reported as per-layer critical path and never as summed-load, so that a metric which understates the recoverable excess by 1.5x to 1.8x cannot size a placement.
31. As a benchmark owner, I want every profile restricted to real forward windows, so that idle dummy-batch work cannot dominate an aggregate.
32. As a benchmark owner, I want results reported as the share of measured recoverable excess recovered, so that a weak policy is distinguishable from an operating point with little to recover.
33. As a benchmark owner, I want a runner to fail loudly when it served no request or captured no annotation, so that a run cannot report success having measured nothing.
34. As a benchmark owner, I want the interconnect and the model shape recorded with every result, so that a conclusion about one node or one expert geometry is never mistaken for a conclusion about the policy.
35. As a benchmark owner, I want the dominant inefficiency named even when it is out of scope, so that this feature is not held responsible for TTFT it cannot reach.
36. As an Ascend operator, I want the placement, lifecycle, failure and benchmark contract preserved, so that CUDA and Ascend results are comparable despite different token communication backends.

## Implementation Decisions

1. **Feature boundary.** The feature stays in vLLM `additional_config` under `predictive_expert_replication`, disabled by default. Enabling it provisions **Expert replication infrastructure** — physical slots, logical and physical maps, transfer buffers, the distinct EPLB communicator — and suppresses Native EPLB's historical window, periodic placement and asynchronous rebalance worker. Enabling both controllers is a configuration error. The profile-run rearrangement still executes, because predictive transfers need the same buffers reserved.

2. **Layout and ownership are unchanged from the previous revision and remain correct.** For 128 logical experts at EP=8, each rank serves 16 canonical physical rows plus one inactive replica row. Canonical ownership never moves. Logical, global physical and local physical expert counts stay distinct. An inactive row is an explicit inactive mapping with zero routed tokens. The layout is uniform across layers even though the leading layers can never be a replica target, because `num_local_physical_experts` is a single model-wide value in vLLM's mixture-of-experts interface.

3. **Source-rank routing is retained as the correctness contract, not the optimisation.** Before dispatch each source rank applies its **source-local physical map** to derive physical routing IDs. That map offers exactly one copy per logical expert, which turns the shared routing path's per-token replica choice into a lookup, so a rank's chunk cannot be split across copies. This was verified on hardware: position-weighted checksums of every physical copy of each logical expert matched on 48 of 48 layers with a replica placed, so routing to either copy is arithmetically equivalent and any output difference can only be summation order.

4. **Prediction stays where it is; its cost is what changes.** The current sparse MoE evaluates the target MoE's gate and router on its own source-local pre-dispatch hidden states, counting **logical** experts, excluding padding via the EPLB unpadded-token device scalar, through a read-only routing seam that applies no mapping and records no actual load. All of that is correct and measured accurate enough: planning from predicted load and scoring on actual load recovers 33.2% of excess against an oracle's 36.8%, and accuracy on the peak rank's own experts — the only ones a placement can choose — is 0.90.

5. **The elementwise tail of predicted-count computation becomes one Triton kernel.** Measured per source layer, prediction adds 17.2 kernels: about 11 to 12 are elementwise steps producing the count vector — padding mask, range check, dtype casts, multiply, clamp, `scatter_add` — and the rest are the gate GEMM, the router's top-k, the snapshot AllGather and EPLB's own load recording. The kernel consumes hidden states, the target gate's logits and the unpadded-token scalar, and emits the int32 per-logical-expert count vector. **It does not absorb the top-k**: that kernel is vLLM's own, shared with real routing, and reusing it is cheaper than maintaining a second implementation that must agree with it. Triton is indicated here because the work spans tokens times top-k, tens of thousands of elements, unlike the planner.

6. **The plan is computed on the device.** Every rank runs the same deterministic reduction over the same allgathered snapshot, so plans are identical by construction and no broadcast or leader exists. At `max_replicas_per_layer = 1` the plan is a single argmax — the hottest expert on the layer's peak rank, placed on the lightest rank that does not already hold a replica for that layer. Integer end to end: the snapshot is int32 and stays integer, because a device argmax over floats is order-dependent and two ranks reducing the same values in a different block order could pick different experts. Ties break on the lower logical-expert id, then the lower rank id.

7. **The retained host planner is the oracle for the device one.** `plan_replicas` and its pure helpers stay in the tree, not on the serving path, because the device argmax must be asserted bit-identical to them. This is why the previous implementation's planner is kept while its orchestration is replaced.

8. **Candidates come from the peak rank, and only positive-benefit placements are returned.** Replicating an expert elsewhere cannot shorten the rank the layer is waiting on. A placement must not raise the peak, and must move at least one `BLOCK_SIZE_M` worth of tokens, since below one block it saves no block and therefore no time. **Source-rank routing sheds exactly half an expert**, because the source ranks divide between the two copies, so reducing the peak is a makespan problem and not a subtraction.

9. **`max_replicas_per_layer` defaults to 1, and this is a correction from measurement.** The online planner sees one layer at a time — when layer `L+1` plans for `L+2`, no later layer's prediction exists — so layers are visited in index order and each fills to the cap until the forward's budget is gone. At a cap of 2 with a budget of 43 that covers `43/2 = 22` layers and always the lowest-indexed 22. Offline at equal budget, a cap of 1 removes 48.0% of critical-path excess against a global-ranking oracle's 48.3%, where a cap of 2 removes 23.5%. Coverage is what drives benefit, because a layer's second replica chases a much smaller expert than its first. Raising the cap requires raising the budget so that `budget / cap` still covers the reachable layers.

10. **The cross-layer ranking in the planning API is retired as a contract.** The previous revision required one candidate list ranked across all layers. That is impossible in-forward by causality, and the code never did it. The per-layer allocation is now the stated design, with the cap as its control.

11. **The transfer lands through a symmetric staging workspace, then a local copy.** The canonical owner issues a stream-ordered one-sided put into the target's staging workspace; the target copies from there into its replica row. Measured: 33.0 us for a 9.00 MiB expert at 285 GB/s, plus 6.3 us for the local copy at the measured 3.00 TB/s HBM bandwidth — 39.3 us, or 0.06% of a 67.87 ms prefill step. **The staging workspace holds one expert and is shared by every layer**, because at most one expert is in flight; a transfer for a later layer must not overwrite a replica a nearer layer still needs.

    Two alternatives were probed and are recorded so they are not re-tried blindly. Registering the model's own weight tensors so a put could target them directly is **not available on this stack**: registration requires a dynamic VMM heap, the VMM heap requires a user allocation handle PyTorch does not create, and the two settings exclude each other. PyTorch symmetric memory **does** work — weights allocated inside its `MemPool` with ordinary tensor semantics, rendezvous across 48 layers at 7.17 GiB per rank, a peer tensor view written by slice at 252 GB/s — and it is the better shape if the staging copy ever matters. It was not chosen because it requires a memory-pool context around expert-weight creation inside the MoE and quantisation paths, where the staged route touches the weight allocation not at all.

12. **Ordering is a stream wait, never a host block.** The target's consumer waits on a CUDA event recorded after the copy; a plain event is sufficient and no fence or flag polling is needed, which was verified. `synchronize()` remains legal only where the host genuinely reads the data, and after this revision there is no such site on the per-forward path.

13. **The routing maps are published by a device scatter.** Routing consumes `source_local_physical_map` and `source_local_replica_count` as device tensors passed into the mapping kernel, so a device-side scatter is sufficient and the host never learns the plan. Publishing must write the **source-local** pair: writing the global pair instead transfers the replica, describes it correctly, and publishes it where nothing reads — a measured run then activated 131 replicas per forward and removed 0.6% of excess against an oracle's 35.1%. The published set is a layer's **complete** desired set, so an empty set is what reverts a replica the previous forward left.

14. **Placement suppression is decided per forward from a value every rank agrees on, before anything is recorded.** Below the **block-quantization bar** the MoE kernel pads every touched expert to the same block count, so no placement can save time; such a forward must not plan, transfer, publish or revert. The count comes from the DP coordination all-reduce's result, already on the host and identical on every rank; the local token count is unusable because it differs by rank. Deciding this after a snapshot has been recorded is what previously made every decode and dummy forward revert all 48 layers.

15. **The block size is read from the kernel configuration, not hardcoded.** The same constant gates suppression and floors the planner's minimum move, so a wrong value either reopens a regime that is settled negative or rejects placements that would have paid. It becomes a cost-profile field checked at startup like the rest of the fingerprint.

16. **`max_transfers_per_forward` counts what its name says.** It currently increments on planned placements before reconciliation, so it bounds coverage rather than bytes. Either the counter moves after reconciliation or the knob is renamed. **`max_concurrent_transfer_bytes` is implemented**: it is the binding constraint on bytes in flight, and it is currently declared and never read.

17. **The hook positions change, and the order of that change is load-bearing.** The launch moves from the head of the following layer's MoE to the **tail of the predicting layer's MoE**, after the snapshot completes, leaving the target layer's Attention as the overlap window; the wait stays at the head of the target layer's MoE. This is only correct once decisions 6, 11 and 13 are in place, because with a host planner the launch and the wait become adjacent statements and the window is **zero**. Until then `prediction_lookahead_layers = 1` is rejected by configuration validation with that reason stated, because it is currently accepted and silently exposes the entire transfer.

18. **Lifecycle.** Each layer holds an active plan, at most one inbound pending plan, a plan version and ownership metadata. Every plan is produced and consumed within the same forward. An empty slot activates immediately. Replacing an occupied slot requires two consecutive hot observations and satisfaction of the enforced minimum residency, which is the greater of the configured value and the number of steps for the predicted per-step gain to cover the exposed transfer. A plan carries its producing layer and forward identity, and a target accepts only the plan produced `prediction_lookahead_layers` positions before it for that forward. `prediction_lookahead_layers` is immutable for the process lifetime. Forward completion asserts no pending plan remains. A version mismatch is an invariant violation, not a fallback.

19. **A hot logical expert has one definition.** `hot_load_ratio` is a candidate pre-filter over the peak rank's experts only. The authoritative gate is the policy's positive-benefit test, and a "hot observation" means the policy would again select the same `(logical expert, target rank)` placement.

20. **Cost profile.** Offline microbenchmarks for per-token expert compute, the per-layer overlap window, rank-pair transfer latency and **usable** bandwidth measured while dispatch and combine are running, plus the selected MoE block size. The fingerprint pins model, dtype, EP size, logical expert count and device name; the configuration validator checks the model-shape entries and the worker checks the device entry, both before readiness. No online calibration. An invalid profile fails startup when the feature is enabled.

21. **Failure behaviour.** If the window does not hide the transfer, the target waits, records exposed time, activates and completes. Transfers are not cancelled, not rerouted to canonical and not discarded. A true communication or copy failure is fail-fast. Prediction error affects placement quality only and never correctness.

22. **Runtime scope.** One node, 8x H100 SXM with NVSwitch, CUDA 13, BF16 Qwen3-30B-A3B, eager execution, TP=1, DP=8, EP=8, `allgather_reducescatter`. DBO, pipeline parallelism and speculative decoding disabled. Qwen3-30B-A3B runs on the V1 model runner, so predictive behaviour belongs in the replication state object both runners share rather than in either runner's EPLB glue.

23. **DeepSeek-V4-Flash is a second phase with its own integration, not a configuration change.** It implements the mixture-of-experts interface so the replication infrastructure applies, but its MoE runs through its own mega-MoE path which bypasses the runner the hooks live in, and its router is the bias-corrected variant that the read-only prediction path currently rejects because routing depends on token identity it does not carry. Its expert weights are FP8 with block scales, so **quantised expert transfer moves in scope for that phase** and the scales travel with the weights. Its ceiling is 5.19% against Qwen's 5.05%, so it brings no additional headroom and is sequenced second for integration cost alone.

## Testing Decisions

A good test here asserts observable behaviour through a public seam and states why in its name or docstring. It does not assert private stream calls, internal ordering, or the shape of an intermediate tensor. The bar is raised by this project's history: five defects each individually made the feature inert or harmful while every test passed, and three of those were of a kind that recurs — a value published where nothing reads it, a budget spent at the wrong granularity, a wait made vacuous. Tests written against a **reference implementation** caught more of these than tests written against expectations, so that shape is preferred wherever a reference exists.

1. **Primary seam: the configured MoE model-forward.** It observes the externally meaningful contract — identical logical routing semantics and output against canonical-only execution, correctly activated replicas, valid distributed forward completion. Existing suites are extended rather than paralleled.

2. **Differential seam: the Triton counting kernel against the current implementation.** The kernel's failure mode is a wrong count, not a crash, so it is tested by equality against the existing elementwise path over randomised hidden states, token counts, padding boundaries, out-of-range ids and empty batches. This is the highest-value new test in the spec.

3. **Differential seam: the device argmax against `plan_replicas`.** Bit-identical plans at `max_replicas_per_layer = 1` over randomised snapshots, including ties, all-zero load, and loads where relocating the peak would not lower it. Retaining the host planner exists for this test.

4. **CPU-only unit tests** for deterministic plan selection, source-rank partitioning, tie-breaking, positive-benefit rejection, cost-profile validation and fingerprint mismatch, residency and hotness transitions including the derived minimum residency, inactive-slot reuse, dummy-forward behaviour, per-forward transfer approval limits, and forward-version ownership. These assert plans and observable lifecycle states, not internal order.

5. **Suppression is tested with the sequence the runner actually produces.** A forward that never records a prediction must not publish, because publishing an empty set reverts. The existing test hands the coordinator a thin prediction instead, which the runner cannot produce, and that is why it passed while the defect was live. Any test of suppression must reproduce the real call order.

6. **Collective-safety tests.** No per-forward path branches a collective on per-rank state; events are waited or synchronised unconditionally; a source-level assertion forbids event polling; no per-rank flag reaches a decision that gates a collective. These are pinned rather than remembered, because two deadlocks came from violating them.

7. **Existing EPLB prior art is extended**, not duplicated: the algorithm, execution, event, fused-MoE-layer, routing and model-runner EPLB suites, including inactive physical rows, the canonical-only normalised layout, weight equality after transfer, and an assertion that predictive mode never invokes native rearrangement on the request path.

8. **Distributed correctness on the target node.** P2P replica transfer and source-rank routing across ranks; generated output compared to a no-replica reference within BF16 tolerance over many forwards; repeated activation, replacement and reclamation without deadlock; a transfer deliberately slowed past its window, verifying the forward waits and records exposed time.

9. **Harness self-checks are part of the deliverable.** Every runner fails loudly when it served no request or captured no step annotation. This harness has three times reported success on a run that measured nothing, and once ran for 26 minutes after its benchmark finished because a teardown waited unbounded on a process that ignored SIGTERM. A run's exit code must mean its arms completed.

10. **Negative configuration tests.** Disabled mode preserves existing behaviour; Native EPLB plus predictive mode is rejected; invalid, missing or fingerprint-mismatched cost profiles prevent readiness; unsupported scope is rejected; a lookahead leaving no valid source layer is rejected; `prediction_lookahead_layers = 1` is rejected until the launch point moves; an injected communication failure follows the fail-fast path; startup normalisation completes before readiness.

11. **Ascend tests** mirror the map, lifecycle and output contract with BF16 tolerance and auto-skip without `torch_npu`. HCCL overlap, zero-count grouped-MatMul behaviour and MC2 run only on an NPU server.

## Out of Scope

- **DP-rank arrival skew, which is the dominant inefficiency measured on this node.** Half the ranks spend 93% of a prefill window waiting in collectives, 340-475 ms per step against the working ranks' 55-79 ms, and collectives are 41% to 77% of a step while the expert GEMM is about 10.6%. Placement cannot move it: balancing reduced the per-layer MoE peak by 6.5% and the collectives rose 27.5%. This feature must not be held responsible for TTFT it cannot reach, and a request-distribution fix would be worth more than everything in this spec.
- **CUDA graph capture of the prediction path.** It is the largest single lever on launch-driven desynchronisation and it contradicts the eager execution this scope mandates, while whether the predictive stream, its events and a per-forward-varying plan are capturable is unverified. It gets an independent exploratory ticket and is not a mainline dependency.
- Batching the per-layer snapshot AllGathers into one. Measured at 9.3 us each and 0.40 ms per forward, 4% of the window they hide in, with a 5% spread between median and maximum — there is no arrival skew here to remove. Collapsing 43 collectives into 1 would save 0.40 ms against a cost measured in tens of milliseconds.
- Token-level routing, and more than one replica slot per rank.
- Replicating one logical expert onto several ranks. Measured and rejected: it sheds at most that expert's share times `K/(K+1)`, always less than the share itself, while two different experts clear the measured need at the same transfer cost.
- Moving canonical ownership, or full expert migration.
- Native EPLB and predictive placement running concurrently.
- Online calibration, EMA-driven decisions, prediction-error fallback, automatic controller switching.
- Allocating the expert weights from a symmetric memory pool so a put can target them directly. Verified to work and recorded; deferred because it requires a memory-pool context inside the MoE and quantisation weight paths for a 6.3 us saving.
- Lazy replica tensor allocation, a distinct expert-GEMM stream, topology-aware alternate P2P sources, direct canonical-only checkpoint loading.
- Releasing the native single-layer expert transfer buffer after startup normalisation. Worth about 144 MiB per rank; the transfer communicator holds a reference to it.
- A non-uniform per-layer replica-slot layout skipping the layers that can never be a target. Worth about 45 MiB per rank; the framework exposes a single model-wide local physical expert count. VMM aliasing cuts the same 432 MiB to about 45 MiB at no benefit cost and is the better answer if the memory matters.
- Decode. Settled negative and gated off: clearing the block-quantization bar needs more than 2048 concurrent decode tokens, and while 80 GB cards now put 5024 in reach at 1024 tokens of context and 2512 at 2048, that only removes the capacity constraint. It does not show that the imbalance then converts into time, and reopening it requires re-asking the whole question.

## Further Notes

- **The stop conditions are part of the contract.** Stop and report a negative result if the measured expert GEMM share of a prefill step is below 8%, or if prediction and placement together cost more than half the measured ceiling. This project has twice reached a conclusion only after building, and both times the arithmetic had been available earlier.
- **What the arithmetic looks like today.** The ceiling is 5.05% of a prefill step on Qwen3-30B-A3B, from a measured 10.76% expert-GEMM share times the 46.96% of MoE time that perfect balance can recover. Prediction with its infrastructure and its 43 host synchronisations costs +7.6% mean TTFT; adding placement takes it to +31.5%. Fusing the elementwise tail removes about 64% of the added launches, and since cost is linear in launches that extrapolates to roughly +2.7%, with the host synchronisations removed on top. **The arithmetic can close, and it is an extrapolation until the kernel exists.**
- **Two numbers carry uncertainty that matters.** The expert-GEMM share is a mean across ranks and spans 8.74% to 15.56% between them, and the step time is set by the peak rank, so the ceiling has a couple of points of band. And the two-arm profiles behind the placement figures do not have strictly paired window shapes.
- **Imbalance is per layer.** Every MoE layer is its own collective waiting on its own slowest rank, so the quantity corresponding to time is the sum of per-layer peaks over the sum of per-layer means. Summing a rank's load across layers first lets different layers' peaks cancel: 1.8852 becomes 1.2356 on Qwen and 1.9622 becomes 1.1090 on DSV4, understating by 1.5x and 1.8x. This error has been made three times in this project, most recently by summing per-rank MoE *time*, which is conserved by balancing and therefore cannot show it working at all.
- **Content decides how much is recoverable**, measured per layer across eight datasets: Korean 89.6% of excess, Chinese 77.8%, Japanese 70.9%, Lean 62.1%, code 59.7%, SQL 59.5%, maths 50.9%, conversational text 32.6%. Non-Latin scripts lead by a wide margin because Qwen3's experts specialise by language. The hypothesis that a narrow vocabulary skews more did not hold: SQL and Lean came out level with code. Never use a synthetic uniform-routing dataset for a headroom number; it is a floor control only.
- **Measured hardware facts for the cost profile.** One BF16 Qwen3-30B-A3B expert is 9.00 MiB and crosses NV18 in 39.9 to 41.0 us at 230 to 237 GB/s, uniform across rank pairs; a one-sided put of the same is 33.0 us; HBM copy bandwidth is 3.00 TB/s; one layer's Attention projections are 20.5 to 23.2 us at up to 128 tokens per rank and 37.5 us at 512; a layer's MoE is 65.2 us at one token per rank rising to 107.4 us at 512; KV capacity is 643,873 tokens per rank. One replica slot on each of 48 layers is 432 MiB per rank against 6.75 GiB of canonical expert weights.
- **Expert geometry matters more than any code in this spec, and the two candidate models are equivalent.** DSV4-Flash does 302 MFLOP of expert work per token against Qwen's 75.5 and halves it again with FP8, which suggested roughly double the headroom. Measured, the shares are 10.58% and 10.76% — indistinguishable, because DSV4's attention is sparse MLA with hash compression at 9-13% of a step against Qwen's 1%, so numerator and denominator moved together. A model with fewer, larger experts remains the largest untried lever; Qwen3-30B-A3B's 128 experts at top-8 is close to the worst case.
- The strong deep-layer cross-layer gate similarity from the literature is validated for this purpose and not assumed: prefill prediction planning from predicted load recovers 33.2% against an oracle's 36.8%, and accuracy on the peak rank's own experts is 0.90. The claim that realistic payoff is the oracle bound times accuracy is wrong and withdrawn — a misled placement moves load onto the true peak, so the quantity can be negative and a product cannot.
- **Bench artifacts are not in git** apart from the cost profile, which is an input. Prompt sets, dumps, traces and logs are regenerable; two prompt sets built from a code dataset contained third-party secrets that had leaked into it and were purged from history.
- Two invocation rules, each of which cost runs. Use `python3 -m vllm.entrypoints.openai.api_server`, never the console script, which leaves the tree off `sys.path`, silently loads the installed build and ignores `--additional-config`. And never resolve the `bench` extra as a whole; it can replace the build under measurement.
