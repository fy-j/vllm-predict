# Predictive expert replication for MoE inference

Status: ready-for-agent  
Labels: ready-for-agent  
Scope: initial CUDA PoC in the separately pinned vLLM fork; this document also fixes the contract for the later MindSpeed-RL Ascend port.

## Problem Statement

A hot logical expert makes its canonical owner the slowest EP rank. Because token dispatch and combine are collectives, every rank waits for that one rank, so a single hot expert bounds the whole forward. Native EPLB can create redundant physical experts, but it decides placement from a historical actual-load window and periodically changes placement. That delay can leave bursty or phase-changing workloads imbalanced for several forwards.

The serving system needs to predict an upcoming MoE layer's load early enough to create one useful expert replica before that layer executes. It must preserve canonical ownership and output correctness, avoid adding a global synchronization barrier to every replica change, and make its performance claims comparable with both no-replica serving and Native EPLB.

The operator-facing goal is a measurable serving improvement, stated primarily as **lower p99 TPOT at equal RPS**, and equivalently as **higher sustainable RPS under a fixed p99 TPOT SLO**. No numeric threshold is fixed in advance: the initial aspiration discussed was on the order of a few percent of TPOT, but that figure is not a measured or committed target. The threshold that counts as success is derived from the baseline measurement, which establishes how much load imbalance actually exists and therefore how much is available to recover.

## Solution

Add **Predictive expert replication**: a predictive controller that uses the current layer's cross-layer gate to estimate an upcoming layer's logical-expert loads for every valid routed token. It deterministically selects at most one replica placement per layer, copies that logical expert's canonical weights to one inactive replica slot while the intervening layers execute, and enables source-rank routing to the replica only after the target slot is ready.

The distance between the predicting layer and the predicted layer is the **prediction lookahead**, and it is configurable. A lookahead of one layer gives the most accurate prediction but only one Attention block of transfer overlap; a larger lookahead trades prediction accuracy for a proportionally larger overlap window. On interconnects where one expert transfer costs more than one Attention block, a lookahead greater than one is required for the transfer to be hidden at all.

The controller reuses **Expert replication infrastructure**—physical slots, logical/physical maps, weight-transfer buffers, and the distinct EPLB communicator—but does not run Native EPLB's historical placement controller. The initial serving implementation is for Qwen3-30B-A3B BF16 on the pinned latest-vLLM fork. The validated lifecycle and policy contract will subsequently be ported to MindSpeed-RL for Ascend, beginning with its All-to-All path.

## User Stories

1. As a serving operator, I want predictive expert replication disabled by default, so that existing deployments retain their current behavior.
2. As a serving operator, I want enabling predictive expert replication to provision the required replica infrastructure without enabling Native EPLB's controller, so that the two placement policies cannot race.
3. As a serving operator, I want an invalid or missing cost profile to fail startup when predictive replication is enabled, so that a benchmark never silently runs without the feature.
4. As a serving operator, I want a cost profile measured on a different model, dtype, EP size, or device to be rejected at startup, so that stale offline measurements cannot silently produce wrong placement decisions.
5. As a model operator, I want each logical expert's canonical owner to remain fixed, so that replicas improve execution placement without changing model ownership.
6. As a model operator, I want exactly one inactive replica slot per EP rank in the initial PoC, so that memory cost and comparison with Native EPLB are controlled.
7. As a model operator, I want the initial physical layout to contain the rank's canonical experts plus one inactive replica slot, so that every rank can receive one predictive replica.
8. As a serving operator, I want model initialization to finish layout normalization before readiness is reported, so that request TTFT and TPOT exclude startup rearrangement.
9. As an inference request, I want routing to preserve logical expert semantics whether a replica exists or not, so that predictive placement never changes generated output except for normal floating-point execution tolerance.
10. As a source rank, I want all my tokens routed to a given logical expert to use one chosen physical copy, so that the first implementation has deterministic source-rank routing rather than token-level routing.
11. As a distributed worker, I want every rank to derive the same placement plan from the same gathered prediction snapshot, so that no plan broadcast or controller leader is required.
12. As a serving operator, I want the prediction lookahead to be configurable, so that the transfer overlap window can be matched to the interconnect actually installed rather than assumed.
13. As a model operator, I want the layers whose cross-layer prediction is known to be unreliable to be excluded from prediction, so that early-layer noise cannot drive placement.
14. As a serving operator, I want predicted-load communication to overlap current-layer expert compute and expert-weight transfer to overlap the intervening layers, so that replication improves load balance without unnecessarily increasing TPOT.
15. As a serving operator, I want a bound on expert-weight bytes in flight at any moment, so that replica transfer cannot saturate the interconnect that token dispatch and combine already share.
16. As a serving operator, I want the target rank to wait for the received weights before using a new replica, so that a forward cannot execute against partially copied weights.
17. As a serving operator, I want non-participating ranks to proceed normally to the next EP collective, so that replica activation does not add an explicit global activation barrier.
18. As a model operator, I want a replica to remain resident long enough to amortize its transfer, so that transient prediction changes do not cause copy thrashing.
19. As a model operator, I want the minimum residency actually enforced to be derived from the measured transfer cost and the predicted per-step gain, so that a replica is never created that cannot pay for itself.
20. As a model operator, I want an expired replica to be reclaimed only after repeated absence of positive predicted benefit, so that one noisy observation does not unnecessarily change routing.
21. As a serving operator, I want dummy or padding-only forwards to preserve collective ordering while leaving placement unchanged, so that profile and uneven-batch execution remain correct.
22. As a serving operator, I want prediction error to affect only placement performance and never output correctness, so that no online fallback controller is needed in the first release.
23. As a developer, I want plan ownership and forward versions enforced as invariants, so that a plan from one forward cannot be committed by another forward.
24. As a developer, I want a single definition of what makes a logical expert hot, so that the candidate filter and the lifecycle cannot disagree about the same expert.
25. As a developer, I want the shared staging workspace's safety precondition asserted in code, so that reusing existing replication buffers cannot silently corrupt a transfer.
26. As a benchmark owner, I want a measured baseline before any replication code runs, so that the achievable headroom is known before more implementation is funded.
27. As a benchmark owner, I want to know whether MoE execution is expert-weight-bandwidth bound or token-compute bound at the tested operating point, so that a null result cannot be mistaken for a null policy.
28. As a benchmark owner, I want the same replica-slot budget for Native EPLB and Predictive expert replication, so that their TPOT and RPS comparison is fair.
29. As a benchmark owner, I want compute-limited and memory-capacity results reported separately, so that throughput gains are not confused with a reduced KV-cache capacity.
30. As a benchmark owner, I want prediction accuracy reported per lookahead distance, so that the cross-layer similarity hypothesis is measured rather than assumed.
31. As a benchmark owner, I want prediction accuracy expressed as hot-expert set overlap and per-expert count error, so that the metric reflects predicted load rather than raw gate similarity.
32. As a benchmark owner, I want the interconnect recorded with every result, so that a conclusion about this hardware is never mistaken for a conclusion about the policy.
33. As an Ascend operator, I want the later port to preserve the same placement, lifecycle, failure, and benchmark contract, so that CUDA and Ascend results are comparable despite different token communication backends.

## Implementation Decisions

1. **Feature boundary and configuration.** The public feature lives in vLLM `additional_config` under `predictive_expert_replication` and defaults to disabled. The configuration contains `enabled`, `cost_profile_path`, `replica_slots_per_rank`, `prediction_lookahead_layers`, `prediction_skip_first_layers`, `hot_stable_steps`, `min_residency_steps`, `hot_load_ratio`, `max_concurrent_transfer_bytes`, and `max_transfers_per_forward`. The PoC accepts one replica slot per rank, `hot_stable_steps=2`, and `min_residency_steps=4`; unsupported values fail validation rather than suggesting functionality not implemented. Defaults are `prediction_lookahead_layers=2`, `prediction_skip_first_layers=3`, `hot_load_ratio=1.5`, `max_concurrent_transfer_bytes` equal to one expert's byte size, and `max_transfers_per_forward=2`.

2. **Controller exclusivity.** Expert replication infrastructure is enabled when either Native EPLB or Predictive expert replication is enabled. Enabling both controllers together is a configuration error. Predictive mode creates physical slots, maps, transfer buffers, and the separate EPLB communicator, but suppresses Native EPLB's historical-load window, periodic placement, and asynchronous rebalance worker. The profile-run rearrangement still executes in predictive mode, because predictive transfers need the same communication buffers reserved. Actual-load recording remains available, and is required for prediction-accuracy measurement.

3. **Initial Qwen3 physical layout and routing maps.** For 128 logical experts and EP size eight, each rank starts serving with 16 canonical physical rows and one inactive replica row. The implementation keeps distinct logical, global physical, and local physical expert counts. Logical router IDs remain intact for prediction and metrics. Before token dispatch, each source rank applies its source-local physical map to derive the physical routing IDs; this is what lets the same logical expert use canonical execution for one source rank and a replica for another. An inactive physical row is represented by an explicit inactive mapping and has zero routed-token count. The layout stays uniform across layers even though the first `prediction_skip_first_layers + prediction_lookahead_layers` layers can never be a replica target, because `num_local_physical_experts` is a single model-wide value in vLLM's mixture-of-experts interface and a non-uniform layout would fight the framework.

4. **Startup normalization.** The initial PoC may reuse native EPLB loading and then synchronously normalize weights and maps before the server reports ready. It rearranges canonical rows into the fixed layout, clears inactive rows, and records `startup_normalization_ms`. This is not request-path work. Directly loading only canonical rows is a later optimization.

5. **Cross-layer gate binding and prediction input.** The initial Qwen3-30B-A3B scope has a sparse MoE in every decoder layer. After the ordered decoder layers are constructed, each sparse MoE at index `i` binds to the sparse MoE at index `i + prediction_lookahead_layers`. Source layers are the index range `[prediction_skip_first_layers, num_moe_layers - prediction_lookahead_layers)`; layers outside it bind no target, create no plan, and run no predicted-count collective. Excluding the leading layers reflects the measured result that their cross-layer prediction is unreliable. The binding retains the target gate module, never a snapshot of its weight tensor, so normal weight loading and router initialization remain authoritative. A topology that does not place a sparse MoE in every decoder layer is rejected, because a lookahead measured in layer indices would otherwise silently span a different distance. Prediction is phase-agnostic: on source-local current-MoE hidden states before token dispatch, the target gate and target router's own selection semantics produce predicted logical-expert IDs and counts for all valid routed tokens. The predicted counts are indexed by logical expert, never by physical slot, and are produced through a read-only routing path that applies no logical-to-physical mapping and records no actual load. Dummy and padding tokens are excluded. Ranks with no valid tokens contribute zero counts and still participate in the predicted-count AllGather. A pure dummy forward produces no placement or lifecycle update.

6. **Planning API and deterministic policy.** A narrow policy seam accepts a global predicted-load snapshot and returns **one list of candidate placements ranked across all layers**, which the caller consumes up to `max_transfers_per_forward`. It is deliberately not a per-layer answer: the transfer budget is global, so an allowance spent layer by layer cannot express it, and measurement puts uniform per-layer spending 13% to 5% behind global ranking at the same budget (critical path 1.245 against 1.2258 at 86 placements, one and two per reachable layer respectively). `max_replicas_per_layer` is therefore a **per-layer safety cap** — it stops one layer taking the whole budget — and not the allocation target; how many replicas a layer receives is a result of the prediction, not a constant. The first policy is `GreedyPeakReductionPolicy`. All ranks run it locally with deterministic tie-breaking by logical-expert and rank IDs.

    **Objective: reduce the layer's peak rank time.** Each MoE layer is its own collective and waits for its slowest rank, so the forward's MoE cost is the sum of per-layer peaks. Variance below the peak does not affect it. The policy therefore minimizes the peak, not the spread, and the imbalance it reads must be the per-layer critical-path kind, never the kind obtained by summing layers before comparing ranks.

    **Candidates come from the peak rank.** Only logical experts owned by the layer's current peak rank are considered: replicating an expert elsewhere cannot shorten the rank the layer is waiting on. Only positive-benefit placements are returned, judged after exposed, amortized transfer cost.

    **Across layers, rank by predicted peak reduction** — the only quantity comparable between layers. **Within a layer the choice is not load-bearing**, and this section has now been written three ways, so the measurement is recorded rather than a rule. Both candidate rules carry the positive-benefit test, which is not optional: a placement must not raise the peak. With it, and on data whose two load views are on one scale, taking the hottest expert on the peak rank and taking the largest single-step reduction give *identical* results at one placement per reachable layer (16 of 18 forwards bit-identical), and hottest-first is ahead on 18 of 18 forwards above that, by 0.005 of critical path at 86 placements and 0.015 at 129 — one to three points of excess removed. Neither starves. Two earlier claims here were artifacts and are withdrawn: that hottest-first was clearly better (measured *without* the positive-benefit test, so it could overshoot) and that hottest-first starves at three placements (measured on a per-rank load view that was on the wrong scale — see `bench/RESULTS.md`, the 2026-08-25 correction). Implement either; prefer hottest-first for its slight edge and lower cost, and do not re-litigate this from figures predating that correction.

    **A ratio-targeting solver was tried and is rejected.** UltraEP binary-searches
    the achievable imbalance ratio and lets the placement count follow, which is the
    right shape for a global budget and was implemented and measured. It loses to the
    step-at-a-time greedy on 18 of 18 forwards at every budget tried, because a
    discrete move cannot hit a continuous target: source-rank routing moves exactly
    half an expert, so a layer either falls short of the ratio or overshoots it, the
    search calls both infeasible, and the budget is spent for nothing. Do not re-try
    it from the paper — the solver is not where that work's advantage lives; its
    routing granularity is. See `bench/RESULTS.md`, 2026-08-25.

    **What a replica actually sheds.** Source-rank routing splits the source ranks across the copies, so one replica moves **half** an expert's load, not all of it, and the target rank gains that half. A model that credits a replica with the expert's whole load overstates its reach by about 2x and was used in error here. Reducing the peak is therefore a makespan problem, not a subtraction: after enough placements the target becomes the peak.

    **Several distinct experts, not one expert spread wider.** A layer may place replicas of up to `max_replicas_per_layer` *different* experts, each on a different target rank. Target ranks are necessarily distinct because a rank holds one replica slot per layer, and are chosen from the lightest ranks. The alternative — replicating a single expert onto several ranks — was measured and rejected: spreading one expert of share `s` over `K` ranks sheds at most `s * K/(K+1)`, always less than `s` itself, and the measured hottest-expert share (33.6% of its peak rank) is already below the measured need (39.6%), so no fan-out suffices while two different experts do.

    **Per expert, whole source-rank chunks.** For each placed expert the policy sorts that expert's source-rank chunks by predicted load and assigns each whole chunk to the lighter of the canonical owner or the replica target. It never token-splits a chunk. Granularity is not a limitation here: the subset sums of eight chunks give 256 achievable split points.

    Across layers within one forward, the transfer budget still binds. A layer placing `K` replicas costs `K` transfers, so `max_transfers_per_forward` counts transfers rather than layers, and the enforced minimum residency must amortize all `K`.

7. **Single definition of a hot logical expert.** `hot_load_ratio` is only a cheap candidate pre-filter, applied to the peak rank's experts: a logical expert is a candidate when it is owned by the layer's peak rank and its predicted load exceeds the layer's mean predicted expert load times the ratio. Filtering by absolute hotness alone would admit experts on ranks the layer is not waiting for, and could exclude the one whose removal actually shortens the peak. The authoritative gate is the policy's positive-benefit test. A "hot observation" in the lifecycle means the policy would again select the same `(logical expert, target rank)` placement, not a separate threshold comparison. There is therefore exactly one source of truth for hotness, and no state in which a threshold calls an expert hot while the cost model rejects it.

8. **Static cost profile.** Planner inputs are offline microbenchmarks for per-token expert compute, per-layer Attention overlap window, and rank-pair transfer latency and usable bandwidth. The profile carries a fingerprint pinning model, dtype, EP size, logical expert count, and device name; the configuration validator checks the model-shape entries and the worker checks the device entry, both before readiness. The cost fields are `expert_compute_us_per_token`, `attention_window_us`, `transfer_latency_us`, and `usable_transfer_bandwidth_bytes_per_us`. Usable bandwidth means bandwidth measured while token dispatch and combine are running, not idle point-to-point bandwidth, because the token collectives and the expert transfer share one interconnect and an idle figure systematically overstates benefit. No online calibration or EMA is used in the decision path. The one-time transfer cost is compared with the enforced minimum residency's worth of predicted compute gain. An invalid profile fails startup when the feature is enabled.

9. **Communication ownership and order.** EP's existing communicator continues token dispatch and combine. The separate EPLB communicator performs predicted-count AllGather and expert-weight P2P, using one ordered predictive communication stream. Cross-layer gate evaluation produces source-rank-local counts before dispatch; the predicted-count AllGather starts only after current-layer dispatch and overlaps that layer's local expert GEMM. It completes before the current layer's combine. The snapshot is small enough that this window is not a constraint. A pinned CPU snapshot lets the deterministic planner finish before the target layer's Attention begins. Only the canonical owner sends and only the replica target receives weights in the MVP; topology-aware alternate senders are deferred. The predicted-count AllGather and the expert-weight P2P both use the EPLB group, which is a distinct process group from the EP group precisely so an in-flight predictive transfer cannot block a token collective.

10. **Overlap and no extra global fence.** The planned P2P is launched on the predictive stream and overlaps the layers between the predicting layer and the target layer. "Overlapped" means both that the transfer is concurrent with compute and that it does not make that span's interconnect the new bottleneck; `max_concurrent_transfer_bytes` bounds expert-weight bytes in flight for exactly this reason, and it is the binding constraint rather than a per-forward count, because two approved transfers can otherwise overlap the same layer's dispatch. Source and target synchronize the communication only where their own dependency requires it. Other ranks may reach the following EP collective earlier and naturally wait there for participating ranks. There is no additional EPLB-group all-reduce or barrier for replica activation.

11. **Safe replica replacement and staging reuse.** A target receives P2P data into a shared staging workspace. Because at most one expert is in flight, the staging workspace holds one expert, not one per layer, and the PoC reuses the leading row of the already-allocated expert transfer buffer rather than allocating new memory. Reusing that buffer is safe only while nothing else touches it during serving, so predictive mode asserts that native rearrangement is never invoked on the request path; this assertion is the stated precondition of the reuse and must be explicit in code, not implied by the suppression logic elsewhere. Before a staging-to-slot copy overwrites a slot, the predictive stream waits for the event recorded when that slot was last read by a MoE kernel. It then copies into the slot and records `replica_weight_ready`. The target layer's default stream waits for this event; only then does it promote `pending_plan` to `active_plan` and expose the new map to routing. Maps are never mutated concurrently with router reads.

12. **Lifecycle and plan ownership.** Each layer holds an active plan, at most one inbound pending plan, plan version, and ownership metadata. With a lookahead greater than one, several plans are in flight across the model at once, but each layer still receives at most one, and every plan is produced and consumed within the same forward because of the source-layer range. An empty slot may activate immediately. Replacing an occupied slot requires two consecutive hot observations and satisfaction of the enforced minimum residency. The enforced minimum residency is the greater of the configured `min_residency_steps` and the number of steps needed for the predicted per-step gain to cover the exposed transfer cost, so a replica that cannot pay for itself is never created. After residency, a replica becomes inactive only after two consecutive observations show no positive benefit. A plan includes its producing layer and forward identity. The model increments a monotonic forward identity; a target accepts only the pending plan produced by the layer `prediction_lookahead_layers` positions before it for that same forward, then clears pending state. `prediction_lookahead_layers` is immutable for the lifetime of the process, because ownership checking is defined in terms of it. Forward completion asserts that no pending plan remains. With eager execution and `virtual_engine == 0`, a version mismatch is an invariant violation and fail-fast protection, not a fallback path.

13. **Slow and failure behavior.** If the overlap span does not fully hide P2P, the target waits for `replica_weight_ready`, records exposed wait, activates the plan, and completes the forward. The implementation does not cancel a launched transfer, reroute back to canonical, or silently discard the plan. A true NCCL, HCCL, or copy failure is fail-fast. Prediction error never triggers immediate fallback or online correction; it is measured for later analysis only.

14. **Initial runtime scope.** The CUDA PoC targets one node with eight RTX 5090 GPUs, CUDA 12.8 or newer, BF16 Qwen3-30B-A3B, eager execution, TP=1, DP=8, EP=8, and the `allgather_reducescatter` token backend. DBO, pipeline parallelism, and speculative decoding are disabled. Qwen3-30B-A3B runs on vLLM's V1 model runner, so predictive behavior belongs in the replication state object that both model runners share rather than in either runner's EPLB glue. The initial Ascend port targets BF16/unquantized Qwen3-30B-A3B, eager execution, DBO disabled, and `virtual_engine == 0`; it starts with the available All-to-All path. MC2 decode support is deferred until an environment with at least 16 ranks is available.

15. **Interconnect is a first-class result dimension.** The RTX 5090 has no NVLink, so every inter-GPU transfer traverses PCIe Gen5 x16 and one expert costs far more than one layer's Attention. This makes the target machine the least favorable environment for the policy, and it is why a configurable lookahead is a requirement here rather than an optimization. Every reported result records the interconnect, and a conclusion reached on a PCIe-only node is recorded as a conclusion about that node, not about the policy. This matters for the Ascend port, whose interconnect is expected to be more favorable.

16. **Observability.** Normal serving keeps only low-overhead counters. Benchmark mode may collect detailed timing for predicted-count AllGather, planning, P2P, overlap window, exposed wait, hidden ratio, replica switches, replica-routed tokens, and predicted versus actual peak load. It also records prediction accuracy per lookahead distance as hot-expert set overlap and per-expert count error, computed against the recorded actual load; raw gate-logit similarity is not the reported metric, because a high logit similarity can still reorder the selected top-k and therefore mispredict load.

17. **Workload matrix.** Two request shapes are fixed, chosen to separate the phases: **2k prompt / 1k decode** (prefill-weighted) and **1k prompt / 2k decode** (decode-weighted). Each runs over three content domains, because expert routing is content-dependent and a domain that concentrates on fewer experts has more imbalance to recover: conversational text, code, and mathematical reasoning. Decode length is forced so that TPOT is comparable across baselines; prompt length is obtained by filtering real samples to the target within a tolerance band, never by padding with synthetic tokens. Two controls accompany every sweep: a length-exact real-text control, and a uniform-routing control built from synthetically generated token sequences. The synthetic control establishes the imbalance floor and must never be reported as a serving result, because sequences generated by sweeping the vocabulary route almost uniformly across experts and therefore understate the imbalance that real content produces. Imbalance and recovered gain are reported per domain and per request shape, not pooled, since the policy's value may be domain-dependent.

18. **Benchmark contract.** A measured baseline precedes replication work and decides whether it proceeds: if the observed EP rank load imbalance at the tested operating point is smaller than the achievable gain net of transfer cost, implementation stops rather than continuing. Every reported configuration uses the same model, request mix, hardware, and slot budget. The three mandatory baselines are no EPLB/no replica, Native EPLB with the same redundant-slot count, and Predictive expert replication. Benchmarks run at the highest achievable ratio of per-layer MoE time to the local expert-weight read floor, and every result reports that ratio, so that a null result cannot be confused with an operating point where load balance cannot convert into time. A comfortably token-compute-bound decode regime is not reachable on 32 GB cards: KV capacity caps decode concurrency, which caps the ratio in the neighbourhood of 1.4 to 1.8. The ratio is therefore a reported condition of every result, not a precondition the benchmark can be configured to satisfy. Compute-limited measurements report fixed-RPS TPOT, TTFT, end-to-end latency, EP load distribution, and maximum sustainable RPS under a p99 TPOT SLO. Memory-capacity measurements separately report KV blocks, peak memory, maximum concurrency, and the OOM boundary. Startup normalization is separately reported and excluded from serving latency. Success is judged against the headroom that baseline measurement established, not against a threshold chosen beforehand: every result reports the measured peak-versus-mean rank imbalance at that operating point, the share of it the policy recovered, and the p99 TPOT and sustainable-RPS deltas against both baselines. Reporting "recovered X of the Y available" is the required form, because an absolute percentage alone cannot distinguish a weak policy from an operating point with little to recover.

## Testing Decisions

1. **Primary integration seam.** Test through the existing configured MoE model-forward seam, because it observes the externally meaningful contract: identical logical routing semantics and output versus canonical-only execution, correctly activated replicas, and valid distributed forward completion. Do not test private stream calls as the primary proof of correctness.

2. **Planner and lifecycle unit tests.** Use CPU-only tests for deterministic `ReplicaPlan` selection, source-rank partitioning, tie-breaking, positive-benefit rejection, cost-profile validation and fingerprint mismatch, residency/hotness transitions including the derived minimum residency, inactive-slot reuse, dummy-forward behavior, per-forward transfer approval limits, and forward-version ownership under a lookahead greater than one. Test the Qwen3 cross-layer-gate registry binds each sparse MoE to the MoE `prediction_lookahead_layers` ahead, leaves the skipped leading layers and the trailing layers unbound, and rejects an unsupported non-adjacent topology. These tests assert plans and observable lifecycle states, not internal implementation order.

3. **Existing EPLB state and rearrangement prior art.** Extend the repository's existing EPLB algorithm, execution, event, fused-MoE-layer, routing, and GPU-model-runner EPLB test suites rather than creating parallel test infrastructure. In particular, test the existing map and weight-rearrangement seam with inactive physical rows, canonical-only normalized layout, and weight equality after transfer. Assert that predictive mode never invokes native rearrangement on the request path, since that is the staging-reuse precondition.

4. **Prediction accuracy seam.** Compare the Global predicted-load snapshot against the recorded actual load for the same layer and forward. This seam is read-only and needs no replication machinery, so accuracy versus lookahead distance is measurable as soon as the prediction path exists. Report hot-expert set overlap and per-expert count error, not gate-logit similarity.

5. **CUDA distributed correctness.** On the eight-GPU RTX 5090 target, verify P2P replica transfer and source-rank routing across ranks; compare logits or generated outputs to no-replica reference within BF16 tolerance; verify all ranks complete repeated replica activation, replacement, and reclamation without collective deadlock. Exercise a transfer that outlasts the overlap span and verify the forward waits and records exposed time.

6. **Negative configuration and failure tests.** Verify disabled mode preserves existing behavior; Native EPLB plus Predictive mode is rejected; invalid, missing, or fingerprint-mismatched cost profiles prevent readiness; unsupported initial scope is rejected; a lookahead that leaves no valid source layer is rejected; and a deliberately injected communication failure follows the fail-fast path. Verify startup normalization completes before readiness and never becomes first-request TTFT work.

7. **Ascend tests.** Add BF16-tolerant integration tests for the same map, lifecycle, and output contract. They must auto-skip when `torch_npu` or the required distributed environment is absent. Actual HCCL overlap, zero-count grouped-MatMul behavior, and MC2 tests run only on an NPU server.

8. **Performance validation.** Before interpreting serving results, capture the interconnect topology, NVLink presence, P2P bandwidth and latency, and NCCL test results. Report the per-layer interconnect utilization already consumed by token dispatch and combine, because that is what the expert transfer competes with. A topology without usable P2P is reported as an environment limitation rather than evidence for or against the policy. Run all three baselines and both benchmark families using the metric contract above.

## Out of Scope

- Token-level routing, or more than one replica slot per rank.
- Replicating a single logical expert onto several ranks. Measured and rejected rather than deferred: it sheds at most the expert's own share times `K/(K+1)`, which is below the measured need at every fan-out, while placing two different experts clears it at the same transfer cost.
- Moving canonical ownership or full expert migration.
- Native EPLB and Predictive expert replication operating concurrently.
- Online calibration, EMA-driven decisions, prediction-error fallback, or automatic controller switching.
- Lazy replica tensor allocation, a distinct expert-GEMM stream, topology-aware alternate P2P sources, and direct canonical-only checkpoint loading.
- Releasing the native single-layer expert transfer buffer after startup normalization. This is a quantified follow-up worth about 144 MiB per rank, deferred because the transfer communicator holds a reference to that buffer and reclaiming it means changing the communicator's lifetime.
- A non-uniform per-layer replica-slot layout that would skip the layers which can never be a replica target. Worth about 45 MiB per rank, deferred because the framework exposes a single model-wide local physical expert count.
- Reducing dynamic MoE workspace peak through better balance as a stated goal. The workspace is sized from the scheduler's maximum batched tokens rather than from observed balance, so this is treated as a hypothesis to disprove during baseline measurement, not a benefit to claim.
- Quantized or mixed-quantization expert transfer support.
- DBO, nonzero virtual engines, pipeline parallel scheduling, speculative decoding, and broader model-family support in the first PoC.
- Ascend MC2 decode implementation or validation before a 16-rank-capable NPU environment is available.

## Further Notes

- The initial CUDA work belongs in the separately pinned latest-vLLM fork, not in MindSpeed-RL. MindSpeed-RL remains the home for the later Ascend adaptation and its tests.
- Measured on the target node, for reference and for seeding the cost profile: one BF16 Qwen3-30B-A3B expert is 9.00 MiB; a point-to-point expert transfer costs about 175 microseconds at about 54 GB/s, uniform across all rank pairs; one layer's Attention projections cost about 25 to 31 microseconds at up to 128 tokens per rank and about 98 microseconds at 512; one layer's MoE expert compute costs about 102, 191, and 546 microseconds at 32, 128, and 512 tokens per rank; and reading a rank's 144 MiB of local expert weights costs about 84 microseconds. One replica slot on each of 48 MoE layers is about 432 MiB per rank against about 6.75 GiB of canonical expert weights.
- KV cache per token is 96 KiB with this model's grouped-query attention, so a 32 GB card holds roughly 150 to 170 thousand KV tokens per rank after weights and workspace. At 2 to 3 thousand tokens of context that is only about 50 to 83 concurrent sequences per rank, which places the decode-phase ratio of MoE time to expert-weight read floor at roughly 1.4 to 1.8. The decode-weighted shape, which is where the TPOT goal lives, is therefore structurally confined to a weakly token-compute-bound regime on this hardware. This is a capacity ceiling rather than a tuning problem.
- Two consequences follow from those numbers and drove this revision. First, a transfer costs several times one layer's Attention, so a lookahead of one cannot hide it on this node. Second, at low tokens per rank the measured MoE time is close to the expert-weight read floor, which means load imbalance cannot convert into time there; the benefit only exists once MoE execution is token-compute bound.
- Token dispatch and combine already consume a substantial share of per-layer interconnect bandwidth in this configuration, so an expert transfer is not free even when it is concurrent with compute. This is why the cost profile records usable rather than idle bandwidth.
- The paper's strong deep-layer cross-layer gate similarity is a hypothesis to validate with prediction metrics and serving outcomes, not a correctness assumption. Prior experiment on this workload found cross-one-layer gate logit similarity above 95%, degrading with distance, and unreliable prediction in the first three layers; those observations set the lookahead and skip defaults but are not a substitute for measuring set overlap and count error.
- The startup-normalization choice intentionally prioritizes a fast, low-risk PoC. It may temporarily load redundant rows that serving does not retain; that cost belongs to startup accounting only.
- No repository ADR conflicts were found for this work.
