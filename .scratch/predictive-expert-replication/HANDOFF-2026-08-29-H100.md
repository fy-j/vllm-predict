# Handoff — continuing on an 8-GPU H100 node

You have not seen this work before. This gets you productive without reading the whole
history. Everything here is measured on **8x RTX 5090, PCIe Gen5, no NVLink**, with
Qwen3-30B-A3B, DP=8, EP=8, `allgather_reducescatter`, eager mode.

Read in this order: this file, then `CURRENT-STATUS.md` (its first two sections), then
the ticket you pick up. `spec.md` is the contract; `glossary.md` defines the terms.
`AGENTS.md` at the repo root is binding — in particular, on **your** machine use `uv`
and `.venv/bin/python`, never bare `pip`. (The 5090 node was an exception the operator
granted; do not assume it here.)

## 1. What the feature is, in one paragraph

MoE routing is uneven: some experts get far more tokens than others, so the rank
holding a hot expert becomes the layer's critical path. **Predictive expert
replication** runs layer `i`'s hidden states through layer `i+2`'s *gate* to predict
that layer's expert load before it executes, then copies a hot expert's weights to a
second rank so the load splits. Prediction is what creates the transfer window — with
exact post-gating load there is nothing left to overlap, because routing maps
logical to physical *before* dispatch. One replica sheds exactly half of an expert,
because source ranks divide between the copies (source-rank routing: a rank's chunk is
never split across copies).

## 2. The verdict, so you do not re-derive it

**Built, correct, and net negative on the 5090 node.** It removes about **15-17% of
prefill critical-path excess** against an oracle of ~31-35%, and costs **+11% to +29%
mean TTFT** depending on domain and concurrency.

Why it cannot pay there, in one chain — this is the most important arithmetic in the
project:

    a real prefill window is 66.0% collectives, 4.9% attention/norm,
                             3.67% expert GEMM
    balancing only touches the expert GEMM
    -> removing 16.8% of excess saves 7.91% of GEMM = 0.29% of the step
    -> perfect balance would save 1.73% of the step
    -> measured cost is +11% TTFT

Ticket 00 put the prefill ceiling at 3.3% of a step by assuming MoE was 30% and
movable. The profile says most of that 30% is token dispatch and combine, whose volume
is set by the token count and **not** by expert placement. **The corrected ceiling is
1.37%-1.73%.**

**So the whole question on H100 is one number: what fraction of a prefill window is
expert GEMM when NVLink shrinks the collectives?** Multiply it by ~47% (perfect balance
on the best domain) to get the ceiling. See §5.

## 3. Two measurement traps that cost real runs here

Both are still live. They are why several rounds of analysis pointed the wrong way.

**The `budget=0` arm is not a clean baseline.** Both arms of every runner pass
`predictive_expert_replication.enabled = True`; only the transfer budget differs. So
every TTFT number answers "what does *placement* cost on top of *prediction*", not
"what does the feature cost". Prediction alone measured **19% of TPOT** at concurrency
1 (where the placement gate correctly rejected every forward, so nothing was placed).
A third arm with the feature fully disabled is still missing.

**A profile's aggregate operator table is dominated by idle work.** In a 12.95 s trace
the annotated forward windows covered only the last **0.54 s**; the rest is
`execute_dummy_batch` keeping DP ranks in lockstep while the benchmark client starts
up. Restrict every measurement to the `gpu_user_annotation` events named
`execute_context_*`. Whole-trace totals mix in ~24x more idle work than real work.

**And a third, about the metric itself.** Imbalance is **per layer**. Every MoE layer
is its own collective waiting on its own slowest rank, so the quantity that
corresponds to time is `sum(per-layer peak) / sum(per-layer mean)` —
`imbalance.critical_path_imbalance`. Summing each rank's load across layers first lets
different layers' peaks land on different ranks and cancel: on Korean prompts that
aggregate reads 1.24 against a per-layer 1.90, understating the recoverable excess
**3.7x**. `imbalance.aggregated_imbalance` exists only to show that gap and says so.
This error was made twice in this project.

## 5. What to do on the H100 node, in order

**Step 0, before anything: is it SXM or PCIe?** This decides whether the trip is worth
taking. PCIe H100 has no NVSwitch, so the 8-way collective still crosses PCIe and MoE's
share of a prefill step stays near this node's, which means the ceiling stays near
1.4% and **the feature cannot pay there either**. NVSHMEM and DeepEP also need NVLink,
so ticket 13 is off the table on PCIe.

    nvidia-smi -q | grep -i "product name"   # "H100 80GB HBM3" = SXM; "H100 PCIe" = card
    nvidia-smi topo -m                        # SXM shows NV18; a card shows PIX/SYS
    python3 .scratch/predictive-expert-replication/bench/probe_hardware.py

**Step 1, the number that sets the ceiling.** One baseline profile, no placement, and
measure expert GEMM as a share of a real prefill window. Restrict to the
`execute_context_*` annotations (trap 2 above).

    DOMAIN=ko CONC=8 NUM_PROMPTS=8 OUT_LEN=4 BUDGETS=0 \
      bash .scratch/predictive-expert-replication/bench/run_placement_profile.sh \
      .scratch/predictive-expert-replication/bench/results/h100-baseline

If expert GEMM is still low single digits, the ceiling is ~2-3% and the honest
recommendation is to stop optimising and report that. If it reaches 15%, the ceiling is
~7% and there is something to win.

### Which dataset to run on

Routing is content dependent, so the domain decides how much a placement can recover.
Measured per layer over 12 prefill forwards each, all at 414-456 tokens per expert so
the block regime is comparable (`bench/run_domain_search.sh`, and
`report_domain_imbalance.py` to re-derive):

| domain | dataset | per-layer p50 / max | critical path | recoverable excess |
| --- | --- | --- | --- | --- |
| `ko` | `beomi/KoAlpaca-v1.1a` | 1.84 / 2.91 | 1.8957 | **89.6%** |
| `zh` | `shibing624/alpaca-zh` | 1.74 / 2.58 | 1.7778 | 77.8% |
| `ja` | `kunishou/databricks-dolly-15k-ja` | 1.66 / 2.48 | 1.7090 | 70.9% |
| `lean` | `internlm/Lean-Workbook` | 1.60 / 2.39 | 1.6211 | 62.1% |
| `code` | `likaixin/InstructCoder` | 1.53 / 2.42 | 1.5967 | 59.7% |
| `sql` | `b-mc2/sql-create-context` | 1.56 / 2.18 | 1.5951 | 59.5% |
| `math` | `AI-MO/NuminaMath-CoT` | 1.50 / 2.08 | 1.5094 | 50.9% |
| `text` | `Aeala/ShareGPT_Vicuna_unfiltered` | 1.31 / 1.78 | 1.3263 | 32.6% |

**Non-Latin scripts lead by a wide margin** — Qwen3's experts specialise by language,
and Korean has layers where the busiest rank does nearly three times the mean. The
hypothesis the search was built on, that a narrow vocabulary skews more, **did not
hold**: `sql` and `lean` came out level with `code`, which has the broadest token
distribution of the three original domains and was the least imbalanced of them. Use
`DOMAIN=ko` for the main run and `zh` as an independent second point.

Prompt sets are **not in git** (see the note at the end of §4) — rebuild with
`make_prompts.py`, or let `run_domain_search.sh` build them.

**Step 2, a like-for-like end-to-end point.** The 5090 comparison is Korean prompts,
prefill-heavy: `237.49 -> 263.68 ms` mean TTFT (+11.0%), 16.8% of prefill excess
removed, at `results/e2e-ko/`.

    DOMAIN=ko CONC=8 NUM_PROMPTS=400 OUT_LEN=1 \
      bash .scratch/predictive-expert-replication/bench/run_e2e_placement.sh \
      .scratch/predictive-expert-replication/bench/results/h100-ko

Check `connected: true` and that physical per-rank load diverges from canonical
ownership by a non-zero amount — a green run is not a connected one (see §7).

**Step 3, only if SXM:** `probe_nvshmem.py`, then ticket 13.

`activate()`'s `event.synchronize()` -> `wait_event` is worth doing regardless of
hardware and needs nothing new; it is a checkbox on ticket 13.

## 6. Ticket state

Each ticket's own `Status` line is authoritative. Briefly: `01` `02` `03` `06` `10`
done. `00` answered for both regimes — **read both of its recommendation sections**,
the answer differs between decode and prefill. `12` (replica-slot memory, 432 MiB per
rank) and `13` (device-side plan and transfer) are designed and deferred. `04` `05`
`07` `08` `09` `11` unstarted. `09` is the sole owner of the under-load interconnect
bandwidth `04` needs, and its cost profile still carries an *idle* figure.

**Decode is settled negative** and gated off in code: below one block per expert the
MoE kernel pads every expert to the same block count, so the imbalance costs nothing to
begin with. The bar is `M x topk / num_experts > BLOCK_SIZE_M`, which for this model
means more than 2048 tokens in flight *after* the allgather. Do not re-open decode
without changing the model shape.

## 7. Five defects that each, alone, made this feature inert or harmful

Listed because a run can look completely healthy while the feature does nothing, and
because three of them are the kind that recur.

1. **Published into buffers routing does not read.** `_apply_eplb_mapping` prefers
   `source_local_physical_map`; the activation path wrote `logical_to_physical_map`.
   Replicas were transferred, described correctly, and never routed to.
2. **The snapshot copy's event was recorded on the wrong stream**, so the wait was
   vacuous, ranks planned from partly-filled buffers, plans diverged, and the engine
   deadlocked with no error and no traceback.
3. **The transfer budget was spent per layer** rather than per forward: 43 layers each
   took the full budget of 43.
4. **Nothing reverted.** `reconcile` and friends sat uncalled and replicas accumulated.
5. **The budget concentrated on the earliest layers**, covering 6-7 of 48. Coverage is
   what drives benefit: 22 layers removes 16.9%, 6-7 removes 5.0%.

**How to tell a connected run from an inert one**, cheaply: the log line
`Predictive expert replication: activated N replica(s) on layer L` must appear, and the
dumped physical per-rank load must **diverge from canonical ownership**. Zero
divergence means no token reached a replica no matter what else looks right. That probe
is sound: `expert_load_pass` is per *physical* expert and the dump reshapes it
rank-major including each rank's replica row.

**The collective-safety rule**, learned from two deadlocks: no per-forward path may
branch a collective on per-rank state. Events are `synchronize()`d or waited
unconditionally, never polled with `query()`, and gates are computed from values every
rank agrees on — `num_tokens_across_dp_cpu`, or the allgathered snapshot. A test
asserts `.query()` does not appear in the coordinator.

## 8. Prior art we read

**UltraEP** (arXiv:2606.04101, `Dots-Infra/UltraEP`). Three ideas were priced against
this design:

- Its **minimum-tokens-per-replica floor** was adopted: a placement that moves less
  than one `BLOCK_SIZE_M` saves no block, so it saves no time.
- Its **binary search on the imbalance ratio** was implemented
  (`imbalance.place_by_threshold_search`) and **rejected on measurement** — it lost on
  18 of 18 forwards against the simpler greedy. Kept in the tree with the negative
  result recorded, so nobody re-tries it.
- Its **token-level quota routing** is deferred to ticket 11. It absorbs an arbitrary
  quota per replica, where source-rank routing moves exactly half an expert. Adopting
  it would change ticket 03's contract.

Its `weight_sync` sits on the critical path at 706-715 GB/s, which is affordable only
on NVLink — worth remembering when reading its design choices, since several of them
assume that bandwidth.

`reference/ascend-prior-art.md` is read-only timing prior art. The spec overrides it.

## 9. What is not established

Do not let these drift into conclusions.

0. **A code audit on 2026-08-29 found six places where the implementation and these
   documents disagree**, including that the overlap window is not the one the design
   describes, that the online planner is per layer and that this accounts for item 3
   below, and that decode and dummy forwards are suspected to revert every replica.
   Read `CURRENT-STATUS.md`'s "Code audit, 2026-08-29" section before acting on
   anything in this file. Item 3 below is answered there; items 1 and 5 are sharpened.
1. **The feature's total cost** — see trap 1; the third arm is missing. Now ticket `14`,
   and it should run **before** step 2 of section 5: prediction's own exposed cost may
   be the same order as the entire ceiling, which would decide the project without
   reference to the hardware.
2. **Where the residual TTFT goes.** Inside real windows, transfers (5.9 ms), extra
   syncs (+10.1 ms) and exposed prediction AllGather (5.0 ms) account for ~21 ms of a
   ~70 ms gap; the rest is GPU idle. But the two arms' windows are not strictly paired
   (4 versus 6), so even that comparison is weak.
3. **Why 15-17% and not the oracle's 31-35%.** Believed to be the online planner's
   causality — it cannot see later layers' relative value — but unverified. Offline,
   planning from *predicted* load reaches 33.2%, so it is not accuracy.
4. **Cross-forward residency.** Ticket 00 measured -20.0%; this branch measures decode
   with resident replicas at **+3.0%**. The code follows the direct measurement.
5. **Why 14.8% of the prediction AllGather stays exposed** when a layer's window is
   longer than the collective. Suspected contention between concurrent NCCL collectives
   on one device; not verified.
6. **The `partial prefill` band on Korean prompts removed 0.3%** where `full prefill`
   removed 16.8%. Unexplained; possibly a banding artifact, since the arms' forward
   counts differ (62/59). Not a result.
