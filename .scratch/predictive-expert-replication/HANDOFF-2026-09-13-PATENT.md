## 1. 给专利的核心结论

**方案有效，条件是 prompt 足够长。** 端到端 prefill TTFT 有可复现的降低，且吞吐同步提升。

三句话版本：

- 在 8k–32k prompt、并发 8–16、8×H100（DP=EP=8）条件下，**mean TTFT 降低 1.8%–7.7%**，多次交错重复中**逐遍配对全部占优**；
- 机制本身在**关键路径上卸掉 26%–36% 的专家负载失衡**，该数字在真实权重上验证过；
- 吞吐提升幅度**系统性地大于** TTFT 降幅（32k：TTFT −7.73% 对吞吐 +8.35%），因为固定并发下 TTFT 缩短直接提高请求完成率。

### 2.3 必须一并知道的负结果与边界

写专利时如果不知道这些，答辩会被动。

**(a) 短 prompt 上净为负。** 这是方案的适用边界，不是缺陷。

| 条件 | 结果 |
|---|---|
| 1k prompt | 不可读；2 副本槽为 **+5.6%** |
| 1.8k prompt | **+2.29%，0/6**（六遍全部更慢） |
| 3.6k prompt | −2.39%，5/6（刚好转正） |

机制解释：本方案的成本是**每前向**的（预测的 gate 矩阵乘与集合通信不随 token 数增长），收益是**每 token** 的。prompt 短 ⇒ 每次前向携带的 token 少 ⇒ 比值不利。

**(b) 域敏感。** 8k 上按数据集分：`books`（pg19，−2.41%）、`pubmed`（−1.49%）为正；`arxiv`（+0.18%）、`chat`（−0.68%）不可读；**`govreport` 为 +1.12%，3/6（净为负）**，要到 16k 才转为 −2.70%。真实长文档（gov）比拼接文本（ko）更难。

**(c) 所有正收益都是纯 prefill。** 全部实验的 `OUT_LEN = 1`，即 `mean_tpot_ms = 0.0`，**TPOT 从未测量**。输出长度为 1 意味着 prefill 收益没有被摊薄到整个请求上。真实负载输出是数百至数千 token。解码侧**两次记录在案的测量在符号上互相矛盾**（−20.0% 与 **+3.0%**），从未收敛。**这是唯一能否定上述全部结论的变量**，专利说明书里"适用于长 prompt 的 prefill 阶段"这个限定必须保留。

**(d) 让收益最大的配置本身有代价。** 32k 的 −7.73% 是把 `max_num_batched_tokens` 从 8192 抬到 32768 才得到的（让每请求只走 1 次前向而不是 4 次）。但抬这个上限让 **stock 服务器自身恶化 32%**（2859 → 3776 ms）、吞吐掉 24%。绝对落点：

```
                     TTFT      吞吐 tok/s
cap 8192   stock     2858.8     90711
cap 8192   本方案     2786.0     92991   ← 绝对最优
cap 32768  stock     3775.6     69063
cap 32768  本方案     3483.2     74815
```

**本方案在 cap 32768 下的绝对表现，比 cap 8192 下的 stock 还差 22%。** 一个以 TTFT 为目标的运维会选 cap 8192，而在那个配置下 32k 上收益不可读（−2.44%，3/6，基线漂移 9.7%）。所以 32k 那个 −7.73% **不是一个可交付的工作点**，而是"每前向 token 数"这条轴的验证实验：同样的失衡修复量（两组规范失衡都是 1.86，且 cap32768 组卸得更少，31.7% 对 35.8%），收益从不可读的 2.4% 变成 6/6 的 7.7%。

> **这条对专利有利也有害，取决于怎么写。** 有利面：它证明了收益正比于每次前向承载的 token 数，这是方案的核心机理，且给出了因果证据（对照组的失衡量几乎相同）。有害面：不能声称"长 prompt 一律提升 7.7%"。

## 3. 机制侧可写入专利的实现要点

这些是**已实现、已测量、可作为权利要求支撑**的内容。详细描述见 `report.html`，此处只列要点与其证据。

### 3.1 预测：用目标层的 gate 作用于当前层的隐状态

- 某一层的路由由 `logits = hidden_states @ gateᵀ` 决定，而 **gate 权重本来就在手里**。因此用**目标层**的 gate 对**当前层**的隐状态求值，得到的就是目标层自己的专家选择。
- 这**不是启发式猜测，是一次真实的 gate 求值**，唯一误差来源是隐状态旧了一层。
- 关键量是**峰值 rank 自身的分布**，而非全局专家负载——放置只能从最热的 rank 上搬走负载，且只能在该 rank 持有的专家中选择。峰值 rank 自身专家的 recall@1 稳定在 **≈0.95**。
- 预测距离（lookahead）的精度曲线：`34.9 / 34.4 / 33.5 / 32.1%` 的关键路径失衡卸载率，对应距离 `1 / 2 / 3 / 4`，**任何距离下都没有一次前向被做得更差**。但距离由重叠窗口的下界决定，故取 `1`。

### 3.2 设备侧放置：计划全程不到达主机

- 规划、预算记账、路由表发布各由**一次 Triton 内核**完成，**每层的 host 读取计划次数为 0**。
- 效果：一个 placed 层的 **kernel launch 由 132 次降至 2 次**；预测侧由 `2.7 → 1`（gate 矩阵乘、top-8 选择、逐专家计数融合进一个 kernel，128 个专家补齐到 2 的幂使整行 logits 常驻寄存器，五份中间量不再落地）。
- **这是本方案区别于"主机规划 + 周期性重排"的核心特征**，且是实测的：主机等待设备数据曾是总成本的 70%，设备侧规划把这部分彻底移除。

### 3.3 有独立的通信 stream，重叠是真正的并发

- **计算流**按层顺序执行；另有**一条专用预测流**承载权重搬运的全部三步：`put_expert` → `barrier_all` → `drain_expert`。
- 两条流只在**两个事件**处相交：计划写好后 `record` 一个事件，目标层路由前 `event.wait()`。**是流等待，不是主机等待**——主机全程不读取计划、不阻塞。
- `barrier_all` **只阻塞预测流**。若放在计算流，全体 rank 会在那里对齐，等于把等待搬进计算路径。
- **`put_expert` 由设备发起**，由本 rank 是否持有该专家在**设备上依据计划判定**。实测 9.00 MiB 单边写入：**47.6 µs（设备发起）对 53.7 µs（主机发起）**——耗时相同，主机被移除。这解决了 `ncclSend` 的结构性约束（其 peer 是主机 `c_int`，必须在入队时消费，所以主机必须先读到计划、必须先等待）。
- **可见性必须由 barrier 建立，CUDA event 不足以建立它**：一个曾得出相反结论的探针，其检查区间内混入了一次 `dist.barrier()`；去掉那次 barrier 后，**112 个权重张量中有 51 个是错的**。
- 重叠窗口 = 目标层的一段 **Attention**：可用 **37.5 µs**（512 token/rank 时）对搬运所需 **33.0 µs**。该 Attention 本来就要执行，窗口不是额外加入调度的时间。

### 3.4 源 rank 路由：一个副本恰好卸掉半个专家

- 路由表以 `(源 rank, 逻辑专家)` 为键。同一源 rank 上选择同一逻辑专家的 token 必然解析到同一物理副本，故**逐 token 的选择退化为一次查表**，而一个副本**恰好卸掉半个专家**，卸载量永远是整数。
- 卸载上限：一个专家被复制到目标 rank，可卸载的量恒为**其自身负载的一半**。
- 副本槽的暂存区按**窗口位置**索引（不是按层奇偶），使一个窗口内多个传输共用同一缓冲区的碰撞**不可能发生**，而不是"不太可能"。

### 3.5 其他可写入的工程特征

- **预算记账与实际搬运量解耦**：预算计的是"移动了什么"而非"持有什么"。稳态实测每前向仅 **2.7–3.2 次**激活（1 副本槽）与 **17 次**（2 槽），对预算 43/86 有一个数量级的余量。
- **预算耗尽不得回退仍有效的常驻副本**：发布行在计划不可负担时改为携带**常驻**放置。窄设计——`found == 0` 仍然回退，因为那是规划器在判断负载，而非预算事故。
- **静态回退**：任何不可复现的取值都回退到静态的、rank 间一致的属性上；内核选择结果与参照实现**逐位一致**（fp32 强制 IEEE 而非 TF32；bf16 在选前把累加器舍回 bf16；并列取小）。

## 4. 对专利撰写的重要提醒

### 4.1 两个已被实测证伪的设计（不要写进权利要求）

1. **一个源层跨多个目标层做预测。** 已实现、通过 566 个单元测试、上服务器跑过，结果只卸掉 **3.7%** 的关键路径失衡，而"一源一目标"是 **26.8%**。原因：四层的 gate 作用于**同一份**隐状态会选出几乎相同的专家（组内预测分布 L1 距离 16–36，而四个目标实际负载相差 5412–7660）。**四分之三的目标实际上使用了并非自己的分布。**
2. **把窗口快照规约改为设备端 NVSHMEM 实现。** 其天花板为 **8.78 ms**，而缺口为 **17.09 ms**——即使实现为完全免费，方案仍落在 **+4.8%**。**不应构建。**

这两条是"我们试过并否定了"，写进说明书会削弱权利要求的新颖性论证，但**应当留在内部记录里**，以备答辩时说明技术选择路径。

### 4.2 一个方法学提醒（若专利需要引用"不同实现的对比"）

**一个减少了工作量却变慢的探针，不是发现了意外的开销，而是破坏了测量所依赖的某个不变量。** 本项目两次栽在这上面（探针把热专家每前向轮换，导致 4 倍传输风暴，量到 +33.9% 的假成本；以及假快照放出的副本卸不掉任何负载，成本全付、收益归零）。两次的破口都在一行早就在打印的日志里（激活数），不在 TTFT 里。

### 4.3 测量纪律（若专利需要声明数据的可靠性）

本项目的既定判据：**基线自身漂移若超过两臂之差，该轮均值不可读**。已有**三次**仅凭 3 遍重复得出、在 6 遍下翻转或消失的结论（最近一次：`books` 域在 3 遍时是 +0.89%、1/3，6 遍确认后翻成 −2.41%、6/6）。专利引用实验数据时，**优先引用漂移小于效应的那一组**（即本文档 §2.1）。


### 5.2 复现 32k 与"每前向 token 数"那条轴

```bash
bash ./run_32k.sh    # 内部两次调用，cap 8192 与 cap 32768 各一组
```

### 5.3 臂语法

```
<budget>[:<transport>[:<group>[:probe]]]     例：96:device:1:c2
```
- `budget`：`off`（stock）或整数（每前向最大传输次数）
- `transport`：`device`（设备发起，默认）或 `host`
- `group`：预测窗口的源层数，`c<N>` 后缀指定副本槽数
- `probe`：ticket 14 的上界探针（**已知无效，见 §4.2**）

### 5.4 结果解读

- `report_arm_spread.py` 给出每臂均值、漂移与配对
- `check_run_measured.py` 是守卫，**因 `failed != 0` 会整批拒读**。32k 两组数据各有一条越界 prompt（34565 token，超服务端上限）导致每遍固定 4 个请求失败，**因此两组数据未被正式放行**。已确认不构成偏倚（两臂失败同一条 prompt，配对落在同一批 252 个请求上），但若要正式引用，需先修 prompt 文件（裁成统一 32768）并重跑。
- **禁止在测量进行中编辑 `vllm/` 目录**。本项目已因此失败过一次：arm-43 的服务器在两次编辑之间启动，所有 worker 抛 `AttributeError`，400 个请求里 392 个失败。

### 5.5 节点状态

8 张 H100。若需保持 GPU 占用以免 pod 被回收，用 `.scratch/keepalive/`：

```bash
setsid nohup env TARGET_UTIL=0.13 bash .scratch/keepalive/keepalive.sh >/dev/null 2>&1 &
touch /tmp/keepalive.stop      # 停止
```

它在任何外部 GPU 进程出现时**自动让开**（杀掉 worker 并释放 CUDA context），所以跑实验前不必手动停。`TARGET_UTIL=0.13` 实测约 9.5–10% 占用。
